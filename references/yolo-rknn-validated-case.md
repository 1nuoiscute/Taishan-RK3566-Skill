# YOLOv8 RKNN：一次 RK3566 实板验证案例

这是一个用户提供的端到端部署案例，用来补充模型路线的验证顺序和常见故障边界；它不是所有泰山派、摄像头或 YOLO 模型的默认配置。

## 证据范围

## 关键决策记录：为什么采用官方优化导出

该路线不是凭空选择，而是由用户提供的部署参考触发，并经后续实板对照收敛：

1. 用户提供的泰山派 / RK3566 部署文章首先帮助定位到：板端安装了 RK3588 专用 `librknnrt.so`，导致 `init_runtime` 在推理前失败；仅以环境变量替换不生效，必须按该镜像的实际加载路径处理匹配的 RK3566 Runtime。
2. Runtime 修正后，原始 YOLOv8 416 导出图可以在 FP16 下检出，但单次 NPU 推理约 98 ms；INT8 路线虽能推理，却出现低置信度目标丢失的问题。由此确认问题不只是“板端库没装好”，还包括原始导出图的量化/性能表现。
3. 随后采用 Rockchip 官方优化 YOLOv8 导出：将 DFL / 解码从 NPU 图移到匹配的 CPU 后处理，导出为多分支输出，再转换为 320 INT8 RKNN。
4. 该用户板端的后续实测显示：优化 320 INT8 静态图检出成功，摄像头完整循环约 24.5--30.4 FPS，NPU 时间多数约 20--23 ms。相对前述约 98 ms 的原始 416 FP16 推理，它是这次部署效果改善的关键技术变更。

这个结论只说明此用户的模型、数据和运行时组合中，**官方优化导出是比原始导出更有效的候选路线**。它不意味着 INT8 必然提升识别精度，也不替代真实场景验证；本案例后续仍发现原训练模型本身在模糊、倾斜和光照变化场景下泛化不足。

### 已确认事实

- 目标板：RK3566；板端 `rknn-toolkit-lite2`、RKNN Runtime 和驱动均为 2.3.2 / 0.7.2 这一套已安装组合。
- 模型：用户已有单类别 `best.pt`，由 Rockchip 优化的 YOLOv8 导出路径生成静态形状、320 输入的 INT8 RKNN 模型。
- 首张静态测试图已检出 1 个目标；摄像头循环日志在该用户板端约为 24.5--30.4 FPS，NPU 时间多数约 20--23 ms。
- `RKNN_QUERY_INPUT_DYNAMIC_RANGE` 对静态 shape 模型的警告未阻止推理；需以真实的 `load_rknn`、`init_runtime`、`inference` 返回值判断成败。
- 同一用户的实时画面中，大量帧仍漏检。后续对板端原始帧的电脑端复核显示原始模型在困难姿态、运动模糊和光照变化下已不稳定，因此“板端能跑”不等于“识别可验收”。

### 用户选择

- 保留原始 `best.pt`；使用 Rockchip 优化 YOLOv8 导出和板端后处理，而不是覆盖已有模型或继续沿用原始端到端输出图。
- 在该实例中选择 320 INT8 作为后续集成候选；256 与 FP16 只应作为对照，不代表其他项目的推荐尺寸或精度。

### 合理假设

- 模型使用 Rockchip 的优化导出：把 DFL / 解码移出 NPU，产生每个尺度三组输出，再在 CPU 做后处理。这通常比把原始 YOLOv8 后处理留在量化图中更适合 RKNN INT8，但必须由实际输出个数、形状和官方后处理匹配来确认。

### 待验证

- 当前板端的摄像头节点、像素格式、分辨率、曝光和真实端到端延迟；本案例中的候选值不能照抄。
- 模型的类别、许可证、数据集划分、量化校准集和在独立采集会话上的召回率/误检率。
- FP16 与 INT8 的精度差异，以及是否因预处理或量化造成额外退化。

## 可复用部署顺序

1. **先确认模型必要性与数据可用性。** 目标可被颜色、几何或标定稳定解决时，不因 NPU 可用就改用 YOLO。
2. **保留原模型和旧部署产物。** 新 ONNX、RKNN、板端脚本放在独立目录；记录框架、导出提交/版本、Toolkit、Runtime、驱动、输入大小和量化参数。
3. **使用与 RKNN 匹配的官方优化导出。** 导出后检查输入布局、输入尺寸，以及每个输出张量的数量和形状；后处理必须匹配该导出图，不能把原始 YOLO 后处理硬套到优化图。
4. **先用静态图验证完整链路。** 依次记录模型加载、Runtime 初始化、输入张量维度、推理耗时、检测数和带框结果。静态模型若 Runtime 要求 batch 维，输入应显式为 `(1, H, W, C)`；不可把三维图像直接当作通用输入格式。
5. **再测摄像头完整循环。** 分开记录采集频率、NPU 时间、CPU 后处理、显示/推流、发布频率和端到端延迟；不要把单次 NPU 时间写成相机 FPS。
6. **用真实原始帧分诊。** 保存含目标、无目标、远近、倾斜、运动模糊和不同光照的原图；同一批图分别用原始框架模型、板端 FP16（如有）和板端 INT8 跑。这样才能区分数据/模型泛化、导出预处理和量化退化。
7. **按采集会话划分数据集。** 连续相邻帧不可随机分散到训练和验证/测试集；优先补充困难场景并保留独立会话作为验收集。

## 常见信号与处理

| 信号 | 优先判断 | 低风险下一步 |
|---|---|---|
| `need 4dims input, but 3dims input buffer feed` | 板端输入缺 batch 维，不是模型失效 | 查模型输入约定；在确认 NHWC/NCHW 后显式扩展 batch 维 |
| 静态 shape dynamic-range 查询警告 | 可能是静态模型的可忽略查询警告 | 不压制真正错误；继续检查实际推理返回值和输出 |
| 静态图能检出、实时几乎全漏 | 不能直接归因于 NPU | 保存同一批原始帧，分别跑原模型、FP16/INT8 对照 |
| NPU 时间低但网页画面卡 | 瓶颈可能在采集、后处理、编码/推流或日志 | 分项计时；关闭逐帧冗长日志；限制预览帧率 |
| 训练 mAP 很高、真实帧低置信或漏检 | 可能存在相邻帧泄漏或场景覆盖不足 | 按采集会话重划分，扩充模糊、姿态、光照和负样本 |

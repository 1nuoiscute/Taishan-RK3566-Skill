# 验证与证据

## 证据等级

对每个关键结论先标记决策状态，再说明证据来源：

- **已确认事实**：由题目原文、用户材料、当前工程或当前目标板证据直接支持；其中官方原理图、IO 表和官方系统/SDK 文档属于官方事实来源。
- **用户选择**：用户已确认的系统、摄像头、协议、坐标或工程约定。
- **合理假设**：为推进比较或最小验证而暂用的判断，必须写明依据、影响和验证方法。官方 Wiki 的“共建”案例、公开教程或历史工程经验只能作为假设依据或候选路线。
- **待验证**：尚未在当前镜像、内核、目标板、实际场景或完整闭环中确认。

不要用合理假设覆盖用户已确认的接线、协议、安全和评分约束，也不要把待验证项写成实测结论。

## 发布验证层级

发布报告必须分开记录，不能用其中一层替代另一层：

1. **静态检查**：语法、内容、链接、版本、生成产物和仓库卫生。
2. **单元测试**：对探针或工具函数使用可重复输入验证代码行为。
3. **合成行为回归**：用 R1–R7 提示检查 Skill 是否守住信息、接口和安全边界；它不是实板测试。
4. **探针实板基线**：在目标板运行只读探针，保留板卡/镜像、脚本 Git SHA、命令、退出码、JSON、stderr 和脱敏摘要。
5. **项目级端到端验证**：在具体摄像头、模型、协议和执行机构组合上按题目验收；历史个案不能推广为当前项目结论。

实板状态使用四类：**旧版已实板验证**、**当前版本仍有效**、**脚本修改后待复验**、**从未验证/证据不足**。脚本修改只使受影响结论降级，不得抹去对应旧版本的历史事实。

公开证据应采用 `templates/hardware-evidence-record.md`。原始设备节点、串口载荷、用户名和路径默认不公开；可以提交脱敏 JSON、原始文件 SHA-256、字段摘要及脱敏规则。没有原始文件时必须明确写“历史文字记录，无原始产物”，不得补造退出码或命令。

## 验证阶梯

1. **输入验证**：确认系统、设备节点、图像尺寸、像素格式、曝光和采集稳定性。
2. **算法验证**：用固定图像或固定场景验证 ROI、检测、测量、跟踪和失败输出。
3. **坐标验证**：用已知点、标定物、方向测试和单位检查验证坐标转换。
4. **接口验证**：独立检查 UART/GPIO/执行机构，记录原始输入、输出、时间戳和错误。
5. **低风险闭环**：限速、限幅、低能量或空载运行，验证状态机、超时、失效和急停。
6. **题目验收**：按题目时间、距离、角度、同步、漏检/误检和连续运行指标测试。

## 性能记录

不要只报告摄像头标称 FPS。至少分开记录相机实际采集帧率、视觉处理帧率、有效检测/跟踪发布频率、端到端延迟、静态误差、动态误差、丢失率、重捕获时间、CPU/内存/NPU 占用、连续运行时间和异常次数。

未在目标板实测的项目写为“待实测”，并给出测量方法和通过条件。

## 调试记录

每轮联调记录以下信息：

```text
时间：
代码/模型/配置版本：
系统与内核：
输入设备与分辨率：
测试场景：
预期现象：
实际现象：
原始证据：图像、日志、串口帧、时间戳或测量表
当前判断：已确认事实/用户选择/合理假设/待验证
下一次只改变的变量：
```

把“电脑能看到”“程序输出了”“板端执行了”“评分指标达成了”分开记录。

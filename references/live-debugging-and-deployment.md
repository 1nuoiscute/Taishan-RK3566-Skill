# 现场联调、图传与部署

当用户已经进入联调、要求直接执行、正在与队友共用设备，或问题涉及摄像头枚举、图传延迟、服务自启、网络切换、协议更新和板端发布时使用本参考。目标是在不破坏当前可用链路的前提下，给出最短可验证动作，并保留明确回滚点。

## 1. 先冻结当前可用状态

动手前只记录会影响本次修改的事实：

```text
本地文件/提交或校验和
板端实际运行文件及校验和
启动命令或 systemd unit
活动 PID 与设备/端口所有者
配置文件及生效值
摄像头稳定标识与当前节点
网络模式、板端地址和恢复入口
协议版本、坐标、单位、有效性和发布频率
已验证功能与当前故障
```

用户或队友正在联调时，先确认是否允许中断当前进程。不得用宽泛的 `pkill -f`、端口清扫或覆盖式上传误杀无关任务。优先通过已确认的 systemd unit、PID 文件或精确 PID 管理进程。若当前版本能工作，先保留可执行文件、配置和启动方式，再部署候选版本。

## 2. 适配现场节奏

- 用户说“先规划”时，先给变更边界、风险、验证和回滚，不执行高影响修改。
- 用户说“直接改/直接给命令”且授权明确时，先给或执行一个最短安全动作，再简要说明结果和下一步；不要重复整套背景或重新启动无关验证。
- 用户只问原因时先诊断，不擅自修改代码、协议、网络或服务。
- 用户明显焦急时，答案先写“现在执行什么”和“成功/失败看什么”；保留必要安全条件，但避免一次给出难以定位失败位置的超长命令。

现场修改按小事务进行：`预检 -> 单一修改 -> 启动/切换 -> 观测 -> 接受或回滚`。每轮只改变一个主要变量，并给出明确停止条件。

## 3. 摄像头分诊不能跳步

摄像头打不开时按以下顺序判断：

1. **节点是否存在**：`test -e`、`ls /dev/video*`；节点不存在不等于被占用，应先归入枚举、连接或驱动层继续取证。
2. **设备身份**：`v4l2-ctl --list-devices`、`/dev/v4l/by-id/`、`/dev/v4l/by-path/` 或 udev 属性；不要只记住 `video9` 之类易变编号。
3. **节点能力**：确认该节点确实支持 capture、目标格式与分辨率；同一摄像头可能枚举多个不同用途的节点。
4. **所有权**：节点存在后才用 `fuser`、`lsof`、systemd 状态或进程表判断是否占用。
5. **最小打开**：用 `scripts/probe_camera.py` 或现有工程的最小采集路径验证；“能打开”与“连续读帧稳定”分开记录。

不要根据一条 OpenCV `can't open camera` 警告直接断言占用、驱动缺失或设备损坏。结论必须对应到上述某一层证据。

## 4. 图传与录像延迟分层

把链路拆成：

```text
采集 -> 推理/后处理 -> 叠加 -> 编码 -> 服务端队列 -> 无线链路 -> 播放器缓存/解码 -> 录像
```

分别记录采集、视觉处理、编码/发布和端到端时间。若延迟随运行时间持续增长，优先检查无界队列、重复发送旧帧、消费者变慢和播放器缓存；若延迟稳定但卡顿，检查实际发布频率、编码开销、无线丢包和解码能力。

- 实时预览默认采用有界“最新帧”语义，慢客户端应丢弃过期帧，不能让队列无限增长。
- 识别分辨率、图传分辨率和录像分辨率是三个契约。优化预览不得顺带改变识别坐标或验收录像要求。
- VLC、浏览器或其他客户端只是诊断分支；用户明确要求 VLC 验收时，最终必须回到 VLC 链路验证。
- 缓存越小通常延迟越低但更易卡顿。缓存值只能作为当前网络的候选参数，不能写成通用最优值。
- “看起来约 100 ms”只能记为主观现象；需要验收数字时使用同屏时钟、闪光/动作事件或带时间戳帧测量。

## 5. 协议与发布频率冻结

协议修改前读取 `templates/serial-protocol-decision.md`，生成版本化契约并由通信双方确认。至少区分：

- 检测/估计更新频率；
- 串口发布频率；
- 两次新观测之间是保持、预测还是发送无效；
- 预测的最大年龄与超时；
- `valid=0` 时每个字段是否仍有语义；
- 字节序、定点比例、符号、范围、CRC 覆盖范围和测试向量；
- 接收端兼容窗口、切换时刻和回滚版本。

不得因为需要更高发布频率就把重复旧值描述为更高视觉帧率。若使用卡尔曼预测，发送的是“带年龄的预测状态”，不是新的检测；超过已确认时限必须转为无效。协议冻结后，排查 ROI、图传或网络时不得顺带改协议。

## 6. 网络切换与自启

网络切换会主动断开当前 SSH，是一个需要回退的事务：

1. 确认目标连接配置已存在且凭据不写入公开 Skill；
2. 确认切换后的发现方式或地址；
3. 配置超时回退到已验证的维护网络；
4. 网络服务与视觉/串口服务解耦；
5. 告知用户 SSH 何时会断、从哪里重连、失败时如何通过 RST/本地终端恢复；
6. 在无人值守前完成断电、目标热点缺失和切换中断测试。

`systemctl active` 只证明服务管理器认为进程在运行。交付自启还要证明设备出现后的恢复、真实帧/串口输出、图传可连接、崩溃重启、配置生效和回滚可用。

## 7. 部署、核对与回滚

推荐使用版本目录或带版本名的候选文件，避免直接覆盖唯一可用副本。一次部署至少保存：

```text
候选版本标识
本地与板端文件校验和
配置快照
启动/重启结果
首个有效观测或明确失败日志
协议测试向量或端口检查
回滚命令与旧版本验证结果
```

“已上传”“服务 active”“日志出现一帧”分别只是部署、进程和单点证据，不能合并成“全部可用”。最终结论按相机、识别、协议、图传、网络、自启和长时间运行逐项报告；未验证项明确标为待验证。

## 8. 控制侧启动与丢失

视觉与下位机联调时额外检查：

- 目标值是否固定来自题目/配置，是否被首帧意外覆盖；
- 电机或摆杆的软件零位是否有物理回零、绝对传感器或人工水平条件支撑；
- 首个样本是否被错误当成零速度；
- `valid=0` 是否立即使缓存观测失效，而不是继续回调历史位置；
- HOLD/稳定区是否使用持续时间和进入/退出滞回；PID 状态只在明确状态转换时处理，不能每帧反复复位；
- 当前烧录固件是否由正在审阅的源码和配置生成。

发现问题时先区分视觉坐标、协议解析、控制状态机、机械零位和实际固件版本，不能只靠改 PID 参数掩盖上游错误。
